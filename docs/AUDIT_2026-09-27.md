# Revisión de arquitectura, seguridad y cálculos

Base revisada: `8853678bf9f12659d4f2da93875bd19b39e539d3`. Fecha: 27 de septiembre de 2026.

## Evaluación

La separación entre motor financiero determinista, servicio, repositorio y Copilot es una buena base para una aplicación personal. El Copilot usa herramientas de consulta y no tiene herramientas de escritura. Las respuestas financieras siguen dependiendo de la integridad, actualización y cobertura de los datos del motor.

No se considera una auditoría exhaustiva ni certificación de seguridad o precisión bancaria. La revisión incluye el código, pruebas existentes, regresiones nuevas, un motor PostgreSQL local y el servidor HTTP local. No se accedió al Neon real ni a secretos de Vercel, y no se ejecutaron solicitudes reales a OpenAI ni una revisión visual móvil.

## Errores corregidos

| Prioridad | Hallazgo y consecuencia | Corrección |
|---|---|---|
| Alta | La versión 0.8.1 estaba anidada, mientras la raíz ejecutaba 0.8.0 y mostraba Reportes como pendiente. | Integración de 0.8.1 en la raíz y eliminación de la copia duplicada; se conservan funcionalidades y pruebas del tracker. |
| Alta | Confirmar una importación o contribuir a una meta hacía varias escrituras independientes. | Una escritura del conjunto por operación. Estado y auditoría de PostgreSQL se guardan en una única sentencia con control de revisión. |
| Alta | Un error leyendo el JSON local podía sustituir datos reales por valores precargados. | El servidor se detiene preservando el archivo original; solo crea datos iniciales cuando el archivo no existe. |
| Alta | Las pruebas originales borraban `data/user-data.json`. | Ejecución multiplataforma con directorio temporal exclusivo y prueba de conservación ante corrupción. |
| Alta | Fechas imposibles, importes no finitos y plazos enormes podían persistirse o agotar recursos. | Validación previa a escritura/proyección; límites de horizonte y mensualidades; tipos de transacción y reglas de corte válidos. |
| Alta | La deuda total y alertas omitían tarjetas sin snapshot. | Se incluyen tarjetas nuevas, se conserva deuda de tarjetas archivadas y se excluyen operaciones posteriores a `asOf`. La utilización usa deuda/límites de tarjetas activas. |
| Alta | La previsión repetía pagos ya registrados y convertía reembolsos a tarjeta en entradas de efectivo. | Los pagos/reembolsos registrados se aplican como reducción de obligaciones conocidas; no son ingresos líquidos. Estados vencidos no conciliados se muestran como pendientes hoy. |
| Alta | El login no limitaba intentos entre instancias de producción. | Contador atómico por IP en PostgreSQL: 10 intentos por ventana de 15 minutos; IP seudonimizada con HMAC; respuesta 429. |
| Alta | El servidor local sin autenticación escuchaba en todas las interfaces. | Se limita a `127.0.0.1`, valida Host y rechaza orígenes ajenos. El modo local sigue siendo de uso personal en el equipo. |
| Media | Días negativos contaba movimientos y dependía del orden de sus etiquetas. | Conteo de días naturales con saldo de cierre, incluidos días sin movimientos; mínimo basado en cierres diarios. |
| Media | Cuatro sobres redondeados alteraban el presupuesto mensual. | Distribución en centavos con ajuste en el último sobre; conserva el total. |
| Media | Una cuota menor que el interés ocultaba el crecimiento del saldo. | Se conserva el interés no cubierto; se avisa del saldo residual al terminar el calendario. |
| Media | Abonos mayores al principal o fuera del horizonte generaban ahorros engañosos. | Rechazo de sobrepagos y fechas no soportadas. Un abono posterior al siguiente pago requiere actualizar primero el plan. |
| Media | Dos importaciones en revisión podían insertar los mismos movimientos. | Se revalida contra transacciones aparecidas después de la revisión y se rechaza la confirmación desactualizada. |
| Media | Una importación antigua podía reemplazar un estado más reciente. | Se conservan sus movimientos sin retroceder el snapshot vigente. |
| Media | Líneas idénticas se eliminaban silenciosamente; créditos y cargos podían conciliarse entre sí. | Se preservan líneas idénticas con advertencia; se exige signo y compatibilidad de pagos. |
| Media | Una mensualidad del estado se trataba ambiguamente como nuevo capital MSI. | El cargo de una mensualidad se importa como cargo individual, sin inventar capital o un calendario nuevo. |
| Media | Cookies malformadas rompían autenticación; tokens con sufijos extra se aceptaban. | Análisis tolerante de cookies inválidas y validación exacta de la estructura firmada. |
| Media | Login/logout eludían la validación de origen; los límites de cuerpo podían omitirse con datos preprocesados. | Validación de origen anterior a las rutas de autenticación y límites para JSON, texto, buffer y streams. |
| Media | La migración volvía a imponer la configuración de Liverpool en cada lectura. | Solo aplica la migración a versiones antiguas; respeta configuraciones actuales. |
| Media | El ingreso usado en resumen y alerta MSI era una constante. | Se obtiene de reglas mensuales/quincenales vigentes, excluyendo ingresos extraordinarios del sueldo recurrente. |

## Arquitectura y límites que permanecen

- **Usuario único:** contraseña compartida y un agregado `app_state`. No hay aislamiento multicuenta/multiusuario; se necesita identidad y autorización por propietario antes de incorporar otros usuarios.
- **Planes e ingresos precargados:** ingresos, recurrentes, deudas y compromisos existentes provienen de `core/src/seed.ts`. Hace falta llevar su mantenimiento al repositorio y la interfaz, con fecha de vigencia y conciliación del saldo del plan. No se inventaron cambios a tus obligaciones.
- **Proyección aproximada:** intereses con periodos de 30 días y tasas configuradas; no replica todos los contratos bancarios, periodos irregulares o asignaciones de pago. Los abonos reducen obligaciones conocidas por antigüedad; no sustituyen la conciliación bancaria de capital/intereses. Las horas intradía no se conocen.
- **Histórico limitado:** solo se conserva el snapshot vigente por tarjeta. El resumen rechaza fechas anteriores a ese snapshot en lugar de presentar un saldo histórico falso. Se requiere un historial de snapshots para reportes patrimoniales históricos completos.
- **Conciliación de previsiones:** los calendarios precargados de MSI/deuda y las reglas recurrentes necesitan revisión al importar estados más recientes. No hay un vínculo canónico entre cada cargo real, su regla recurrente y cada componente del estado; puede haber solapamientos. Es la siguiente prioridad para análisis predictivos fiables.
- **Persistencia:** el agregado con control optimista evita sobreescrituras concurrentes, pero crece con todas las transacciones, importaciones y conversaciones. Para escalar conviene normalizar estos datos, paginar y definir retención/backups/restauración verificables.
- **PDF y Copilot:** se limita tamaño de subida, páginas PDF y mensaje. Falta contrastar extracción con una colección anonimizada de estados de cada banco y evaluar respuestas del Copilot frente a resultados esperados. No se verificó disponibilidad del modelo configurado con la API real.
- **Seguridad operativa:** se necesitan contraseñas y secretos robustos, HTTPS, configuración de `APP_ORIGIN`, aislamiento entre datos de preview y producción, y protección adicional del borde si se quiere frenar ataques distribuidos. Rotar `SESSION_SECRET` invalida las sesiones existentes.

## Exposición de información en el repositorio público

El repositorio contiene saldos, ingresos, gastos y movimientos históricos precargados en `core/src/seed.ts`, `core/src/legacy-tracker.ts`, `server/src/financial-snapshots.ts` y archivos SQL. Si son datos reales, son visibles al publicar el repositorio. La revisión no cambió la visibilidad, no eliminó esos datos funcionales y no reescribió el historial. Volverlo privado y conceder acceso al conector permite revisar sin esa exposición; para publicarlo conviene sustituir datos personales por ejemplos y limpiar el historial deliberadamente.

## Verificación

- `npm test`: compila ambos proyectos, ejecuta las suites de billing, servicio, importación, forecast, Copilot y tracker, además de 14 pruebas nuevas de auditoría.
- Integración SQL con PGlite/PostgreSQL: estado y auditoría juntos, conflicto optimista, rollback ante fallo de auditoría y contador de login compartido.
- HTTP local: salud, página principal, reportes, planificación, creación de cuenta, rechazos por origen/Host y fecha inválida; archivo corrupto preservado.
- Validación sintáctica de JavaScript y JSON.
- `npm audit --omit=dev`: sin vulnerabilidades reportadas en esta ejecución; no equivale a ausencia de vulnerabilidades en el código.
- Ejecución local: Windows, Node 26.10.0. El workflow añadido solicita Node 24 en Windows y Linux; comprobar su resultado en GitHub antes de fusionar.

## Revisión y despliegue

1. Revisar el diff y las pruebas de la rama de auditoría. Mantener `master` sin cambios hasta aprobar la revisión.
2. La raíz del proyecto en Vercel debe ser la raíz del repositorio, con instalación y `npm run build`. Se eliminó la subcarpeta duplicada.
3. El runtime crea `login_attempts` de forma aditiva. No se modificaron bases de datos reales durante esta revisión.
4. Validar en preview con datos aislados: iniciar/cerrar sesión, importar un estado anonimizado, conciliar, contribuir a una meta y verificar la respuesta del Copilot. No usar la base real para estas pruebas.
5. Solo después de esa validación, fusionar y desplegar; conservar una copia recuperable de los datos y comprobar el dominio real.

Referencia técnica del limitador: [cabeceras de solicitud de Vercel](https://vercel.com/docs/headers/request-headers). El despliegue en Vercel confía en `X-Forwarded-For` proporcionado por su borde; el modo local usa la dirección del socket.
